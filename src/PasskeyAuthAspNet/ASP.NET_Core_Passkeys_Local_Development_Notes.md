# ASP.NET Core Passkeys – Local Development Notes

## Setup

This project uses frontend developed in React (just to have some web UI, not something crucial to the project, could be even static JS/CSS/HTML). Backend is implemented in ASP.NET with .NET10, SQL Server as DB system (run locally in docker).

## Reference

This project was created based on [Passkeys in ASP.NET Core 10: Passwordless Authentication with Identity](https://adrianbailador.github.io/blog/65-passkeys-aspnetcore-identity/).	

## Goal

Test ASP.NET Core 10 Identity Passkeys/WebAuthn during local development, including authentication with an Android phone.

### HTTPS requirement

Passkeys/WebAuthn require a secure browser context.

For local development, browsers allow this exception for:

```text
http://localhost
```

However, accessing the ASP.NET application from the phone using the PC's LAN IP, for example:

```text
http://192.168.0.70:63131
```

is not `localhost` from the phone's perspective. The browser therefore refused to handle the Passkey operation over HTTP.

This made HTTPS necessary for the phone-based approach.

---

# 1. mkcert setup in order to use HTTPS

`mkcert` was used to create a local development CA and HTTPS certificates.

Install the local CA:

```powershell
mkcert -install
```

Find the CA directory:

```powershell
mkcert -CAROOT
```

Important files:

```text
rootCA.pem       <- CA certificate; this can be installed on a test device (such as phone)
rootCA-key.pem   <- CA PRIVATE KEY; NEVER copy/share this
```

The root CA private key is the sensitive asset.

### Generate a P12 directly

PEM files are not required when Kestrel is configured to use P12.

For the Windows hostname and LAN IP:

```powershell
mkcert -pkcs12 SKICEG2 192.168.0.70
```

This creates a `.p12` certificate.

The P12 generated by mkcert uses:

```text
changeit
```

as its default password.

The resulting file can be renamed, for example:

```text
Certificates/passkeys.p12
```

### Android trust

For direct HTTPS access from Android, Android must trust the mkcert local CA.

Install/trust:

```text
rootCA.pem
```

Do **not** install or transfer:

```text
rootCA-key.pem
```

or server private-key files.

When finished with the experiment, remove the development CA from the phone.

If the CA private key was never exposed, removing the CA trust from the phone is generally sufficient for that phone to stop trusting certificates issued by that CA.

# 2. ASP.NET Core HTTPS setup

The ASP.NET Core application was running on Windows.

LAN IP:

```text
192.168.0.70
```

HTTPS port:

```text
63131
```

Kestrel was configured to use the mkcert P12:

```csharp
builder.WebHost.ConfigureKestrel(options =>
{
    options.ListenAnyIP(63131, listenOptions =>
    {
        listenOptions.UseHttps(
            "Certificates/passkeys.p12",
            "changeit");
    });
});
```

The `changeit` password is mkcert's default P12 password.

---

# 3. Passkey ServerDomain

The Identity Passkey configuration was:

```csharp
builder.Services.Configure<IdentityPasskeyOptions>(options =>
{
    options.ServerDomain = builder.Configuration["Passkeys:ServerDomain"];
    options.AuthenticatorTimeout = TimeSpan.FromMinutes(3);
    options.ChallengeSize = 64;
    options.UserVerificationRequirement = "required";
    options.ResidentKeyRequirement = "preferred";
});
```

For the hostname experiment, the intended value (of builder.Configuration["Passkeys:ServerDomain"]) was PC machine name:

```text
SKICEG2
```

---

# 4. First Android approach: LAN IP

The initial idea was to open the ASP.NET application directly from Android:

```text
https://192.168.0.70:63131
```

Static HTML was successfully reachable over the LAN.

HTTPS was also made to work after installing/trusting the mkcert CA on the phone.

However, WebAuthn registration failed at:

```javascript
return await navigator.credentials.create({ publicKey: options });
```

with a browser `SecurityError` indicating that the origin did not match the configured ServerDomain/RP ID.

Important observation:

**The ASP.NET passkey-register endpoint was never reached.**

The failure happened in the browser's WebAuthn validation before the credential was sent to the server.

The problem was that Passkeys require RP IP, which cannot be IP address!

---

# 5. P12 vs PEM

`mkcert` can generate PEM certificates/private keys, but P12 is sufficient for this setup.

The preferred command was:

```powershell
mkcert -pkcs12 SKICEG2 192.168.0.70
```

and Kestrel loads the resulting P12 directly.

No manual PEM-to-P12 conversion is necessary.

---

# 6. Windows hostname attempt

Windows hostname:

```text
SKICEG2
```

The intended setup was:

```csharp
options.ServerDomain = "SKICEG2";
```

and:

```text
https://SKICEG2:63131
```

The certificate could cover both hostname and IP:

```powershell
mkcert -pkcs12 SKICEG2 192.168.0.70
```

However, Android could not resolve:

```text
SKICEG2
```

to:

```text
192.168.0.70
```

This became a DNS/hostname-discovery problem rather than an ASP.NET problem.

---

# 7. TP-Link Archer AX1500

The local router was:

```text
TP-Link Archer AX1500
```

The router can reserve an IP for the PC using DHCP Address Reservation.

The desired reservation was:

```text
SKICEG2 -> 192.168.0.70
```

Typical TP-Link location:

```text
Advanced
  -> Network
    -> DHCP Server
      -> Address Reservation
```

However, the AX1500 did not provide a convenient arbitrary local DNS mapping such as:

```text
passkeys.home.arpa -> 192.168.0.70
```

Therefore, making Android resolve a custom local hostname would require additional local DNS infrastructure.

---

# 8. Why the direct-phone approach was abandoned

The original goal was only to test Passkeys from the Android phone.

The direct-phone route accumulated several separate requirements:

```text
HTTPS
  +
mkcert CA
  +
Android CA trust
  +
LAN connectivity
  +
hostname/DNS resolution
  +
certificate hostname/SAN
  +
WebAuthn origin/RP ID compatibility
```

This was consuming considerably more time than the actual Passkey test warranted.

---

# 9. Final solution

The ASP.NET Core application was kept **local on the Windows machine**.

Instead of making the ASP.NET page directly accessible from Android, authentication was performed through the **Windows authentication broker**.

The working flow was:

```text
ASP.NET application running locally on Windows
            |
            v
     Windows auth broker
            |
            v
       QR code shown
            |
            v
       Scan with phone
            |
            v
    Mobile biometric prompt
            |
            v
       Authentication
```

The phone scanned the QR code and prompted for mobile biometric authentication.

This achieved the Passkey authentication test without requiring:

- Android access to the ASP.NET LAN URL
- Android DNS configuration
- a local DNS server
- hostname resolution for `SKICEG2`
- Android trust configuration for the development CA
- additional LAN certificate troubleshooting

## Practical conclusion

For this local Passkey development scenario, the Windows authentication-broker flow was much simpler than exposing the ASP.NET development server directly to the phone.

The final workflow is:

1. Run ASP.NET locally on Windows.
2. Use the Windows authentication/passkey broker.
3. Display the QR code.
4. Scan it with the phone.
5. Complete the phone's biometric authentication.
6. Continue testing the application locally.

The direct Android/LAN HTTPS approach remains possible, but introduces networking, certificate, DNS, and WebAuthn origin considerations that are unnecessary when the broker provides the QR-code handoff.
